## 1. 三档自述

### 30 秒（电梯版）

> 布丁智服是一个多 Agent 的电商客服系统。用户问题进来先做意图识别——大模型判断、字面相似度、关键词规则三路投票，
> 权重 0.7 / 0.2 / 0.1——输出意图、置信度和实体。编排器再按意图和关键词给通用、技术、账单三个 Agent 打分，
> 主 Agent 处理、辅助 Agent 并行补充。知识库是按意图白名单触发检索的，检索内部是 BM25 加哈希向量融合再 LLM 重排。
> 最后有 Prometheus 指标和 LLM-as-Judge 评测，能看出哪一步退化了。

### 2 分钟（讲"为什么"）

1. **为什么先识别意图，不直接丢给大模型？** 客服的处理动作是分叉的：退款要核订单、登录异常要排障、投诉要转人工。
   只给一个 prompt，模型会"什么都答一点"，还会编造订单状态。把意图定死，才能决定查不查知识库、走哪个 Agent、要不要人工。
2. **为什么多 Agent 而不是多个 prompt？** 三块业务的规范与调优目标不同。拆开后每个 Agent 有自己的 system prompt、
   自己的 Skills、自己的成功率与延迟指标；路由层只做决策。
3. **为什么 RAG 按意图触发？** 寒暄和转人工不需要知识，检索纯浪费，还会把无关片段塞进上下文。
4. **怎么证明它变好了？** 意图用标注集算 Accuracy / Macro-F1；端到端用 LLM-as-Judge 四个维度打分，存 baseline，退化超阈值标记 regression。

### 5 分钟（按链路走，每步只说三件事：做什么 → 怎么实现 → 代价）

例如：
- 「意图识别是 LLM 0.70 + 字符 n-gram Jaccard 0.20 + 关键词正则 0.10 加权，阈值 0.5。**只有一路是模型**，另两路是本地字符串运算；
  而且没做归一化，单靠那两路到不了 0.5，所以模型不可用时结果是 OTHER 而不是硬猜——我选择宁可不猜。」
- 「编排用 `CompletableFuture.supplyAsync` 并行主辅 Agent。代价是没指定线程池，走的是 ForkJoinPool.commonPool，
  和全局共享、没有隔离；好处是复合问题延迟接近最慢的那个 Agent，而不是相加。」
- 「检索融合是 BM25 0.45 + 哈希向量 0.55。这里的"向量"是 256 维特征哈希，不是 embedding 模型——
  省掉外部依赖，代价是语义泛化弱，所以靠 BM25 兜关键词。」

> 💡 这三段式（做什么 / 怎么实现 / 代价是什么）是让面试官相信你真读过代码的最有效说法。

## 2. 主链路（含真实开销）

```
POST /chat
 ├─ 记忆读取  MemoryManager.getContext(userId, convId, message)
 │    Redis: wm:{uid}:{cid} List（LRANGE 0..19）+ summary:{uid}:{cid} String，TTL 都是 86400s
 │    情节记忆：进程内 CopyOnWriteArrayList，自研 256 维 hash 向量扫 top5（注入只取 3 条）
 │    用户画像：ConcurrentHashMap + data/java/memory-store.json
 ├─ 意图识别  IntentRecognizer.recognize           ← LLM #1（temp 0.1, ≤256 tokens）
 ├─ RAG gating  shouldUseKnowledge(intent)         14 查 / 5 不查
 ├─ 检索      KnowledgeToolManager.searchWithRewrite(message, 3)
 │    ├ 查询改写                                   ← LLM #2（temp 0.3, ≤256）
 │    ├ 4 路子查询并行 recallK=5（commonPool）
 │    └ LLM rerank（候选 > topK 才调）             ← LLM #3（temp 0.0, ≤256）
 ├─ 编排      AgentOrchestrator.run → BaseAgent.handle   ← LLM #4（角色 prompt + 动态 Skills）
 ├─ 校验      AnswerVerifier.verify                ← LLM #5（temp 0.0, ≤256）
 └─ 写回      addMessage(USER) + addMessage(ASSISTANT) → updateProfile(@Async)
```

**LLM 调用次数要数准**：主链路固定 **3 次串行**（意图 #1 → 生成 #4 → 校验 #5）；走 RAG 时再加 2 次（改写 #2、重排 #3），**最多 5 次**。
其中 #2、#3 是可降级的辅助调用；但注意 —— #2 改写失败会退化成单查询，#3 候选 ≤ topK 时根本不调。
`ChatResponse.latency_ms` **只统计编排段**（`AgentOrchestrator` 里 `Duration.between`），不含记忆、检索、校验——这点被问到一定要说准。

## 3. 数字速查表

### 意图识别（`IntentRecognizer`）

| 项 | 真实值 |
|---|---|
| **三路 ≠ 三模型** | **只有 1 次 LLM 调用**（`chat("", prompt, 0.1, 256)`）；另两路是纯本地字符串运算 |
| 三路权重 | LLM **0.70** / 字面相似 **0.20** / 正则模式 **0.10**（硬编码，不可配）|
| 语义路实现 | `charNgrams` 取 **n=1,2,3** 拼接去重 → 与 18 意图 × 3 模板 = **54 条模板**做 **Jaccard**，取最大 |
| 模式路打分 | `min(1.0, 0.5 + 0.25×(命中数-1))`：1 命中 0.5，2 命中 0.75，≥3 封顶 1.0 |
| **无归一化的后果** | 单靠模式路最多 **0.10**、单靠语义路最多 **0.20**，**永远过不了 0.5 阈值** → 只有 LLM 能把置信度顶过线（单靠 LLM 需 conf ≥ 0.714）|
| refine 规则 | 融合结果是粗粒度（QUERY/BILLING/TECHNICAL/ACCOUNT/ESCALATION 等）且关键词命中**细粒度**表、且 `best < 0.8` → 用细粒度覆盖。因 `0.7×conf ≤ 0.7 < 0.8` 恒成立，**句中出现细粒度关键词时几乎必然覆盖 LLM 的判断** |
| 置信度阈值 | **0.5**；低于阈值 → 判 `OTHER` 但**保留原分值**（所以 `intent_confidence` 可能是 0.35）|
| 紧急度 | 含 紧急/urgent/立刻→**CRITICAL**；含 今天/马上/尽快 或意图为 ESCALATION/HUMAN_HANDOFF→**HIGH**；COMPLAINT→**MEDIUM**；其余 LOW |
| 意图枚举 | **19 个**（QUERY…OTHER）；另有细→粗分组 `INTENT_GROUPS` |
| 缓存 | `ConcurrentHashMap`，key = 消息 + 最近 3 条 history，**超过 1000 条全量 clear()**，无 TTL/LRU |
| 澄清触发 | `intent==OTHER` 且消息长度 >2 且 `confidence<0.5` → 固定话术"我还不能确定您要处理的是哪类问题…"，`routingReason="低置信度 OTHER 意图，先澄清用户需求"`，只做一轮、无槽位填充 |

### 编排（`AgentOrchestrator`）

| 项 | 真实值 |
|---|---|
| 领域基础分 | general **0.1**，technical / billing **0** |
| 意图加分 | general **+0.55** / technical **+0.75** / billing **+0.75** |
| 关键词加分 | technical、billing **+0.18/次**（封顶 0.45）；general **+0.12/次**（封顶 0.35）|
| 实体加分 | `error_code`→technical **+0.2**；`amount`→billing **+0.15**；`order_id`→general **+0.1** |
| 主 Agent | 分数最高者（**无最低门槛**）|
| 辅助 Agent | **≥0.45 且 ≥ primary×0.55**，且不能是 general |
| 硬规则 | `urgency=CRITICAL` 或意图 `ESCALATION`/`HUMAN_HANDOFF` → 直接转人工，不算分 |
| 并行 | `CompletableFuture.supplyAsync`（未指定 executor → **commonPool**），逐个 `join` |
| 多 Agent 合并 | **结构化字符串拼接**（带 `[technical - 主处理]` 标签），不是二次 LLM 润色 |
| 单 Agent 失败 | 非 general 失败 → 退回 GeneralAgent 再答一次 |
| 路由分 | `(成功率×0.7 + 1/(1+avg_ms/1000)×0.3) × (1−penalty)` |

### 检索（`KnowledgeBaseService` + `KnowledgeToolManager`）

| 项 | 真实值 |
|---|---|
| 切片 | `DocumentSplitters.recursive(500, 80)` 字符；兜底按 500 硬切、无重叠 |
| chunk id | `md5(title_i_前50字)`；metadata 固定 `title / chunk_index / source=pudding-java` |
| BM25 | **k1=1.5、b=0.75**，`idf=ln(1+(N-df+0.5)/(df+0.5))`，手写无倒排索引 |
| 分词 | 小写 + 剥 ASCII 标点 + 空白切词 + **补 2-gram / 3-gram**（中文标点不剥、无停用词、无分词器）|
| "向量" | **256 维 signed feature hashing**（`hash & 1` 定符号，HashSet 丢词频），余弦后负值截 0 |
| 融合 | 两路各**除最大值**归一，**0.45×BM25 + 0.55×vector**（线性加权，不是 RRF）|
| `/chat` 的 topK | **硬编码 3**；配置里 `pudding.rag.top-k=4` **从未被读取**（死配置）|
| 召回宽度 | `recallK = max(topK, 5)` = 5 |
| 查询改写 | 1 原始 + **3** 子查询（temp 0.3、≤256 tokens），失败退化成单查询 |
| 并行召回 | `supplyAsync`（commonPool），`putIfAbsent` 按 chunk id 去重，**原始 query 优先** |
| rerank | 候选 > topK 才调；每条正文截 **180 字**；temp 0.0；失败回退**融合分排序** |
| 超时 | `future.get(30s)` **每子查询**；不 cancel，最坏 4×30=120s |
| 缓存 | key=`query:topK`，TTL **300s**，普通 `HashMap`，无上限 / 无淘汰 / 无命中率计数 |
| 熔断 | 失败阈值 **5**，恢复窗口 **60s**，状态 CLOSED/OPEN/HALF_OPEN |
| 降级 | 返回单条 `id="fallback"` 的伪造结果，**success 仍为 true**，`metadata.fallback=true` |
| 上传上限 | **10MB**（`.txt/.md/.json`）|

### 记忆（`MemoryManager`）

| 项 | 真实值 |
|---|---|
| Redis key | `wm:{uid}:{cid}`（List，`leftPush` + `LRANGE 0..19`）、`summary:{uid}:{cid}`（String），TTL **86400s** |
| 压缩触发 | `LLEN >= compress-at=15`，**同步执行**（无 @Async）|
| 压缩后保留 | **只留最近 5 条**（`keep=min(5,size)`）|
| 摘要 prompt | `用 2-3 句话总结以下对话关键信息：…`，temp 0.0 / ≤256 tokens，失败兜底"对话包含 N 条历史消息。" |
| 上下文拼装 | `[会话摘要]` → `[相关历史]`（检索 top5，**只注入 3 条**）→ `[用户画像]` → `[最近对话]`（≤20 条）|
| 画像 | `updateProfile` **@Async**，每次 /chat 调一次，取最近 10 条，temp 0.0 / ≤512 tokens |
| 画像存储 | **JVM ConcurrentHashMap + `data/java/memory-store.json`**（全量重写）—— **不在 Redis** |

### 监控（`PerformanceMonitor`）

| 项 | 真实值 |
|---|---|
| 采集频率 | `@Scheduled(fixedDelay = 10000)`，即 **10 秒**；**没有 cron** |
| 自定义指标 | `pudding_agent_success_rate`(Gauge) / `pudding_monitor_collections_total`(Counter) / `pudding_monitor_collection_duration`(Timer) |
| 惩罚公式 | `min(0.9, min(0.5,(0.90−sr)×2) + min(0.4,(avg−3000)/10000))`，**0.90/3000 是硬编码字面量** |
| 告警条件 | `sr<0.90` 或 `avg>3000ms`；`alertKeys` 永久去重、`resolved` 恒 false、**无恢复逻辑** |
| webhook | 仅 `webhook-url` 非空才 POST；`RestClient` 无超时、无重试、异常全吞 |
| 生效点 | `bestAgent` 在**同类型实例间**取 `routingScore` 最大者 |

### 评测（`EndToEndEvaluator` + `LLMJudge`）

| 项 | 真实值 |
|---|---|
| 默认用例 | **8 条意图 + 4 条对话**（3 单轮 + 1 三轮）硬编码 → 14 条 result，约 **26 次 LLM 串行调用** |
| 意图判定 | `predicted.equals(expectedIntent)`，**expectedIntent 未小写**（传大写必错）|
| 指标 | accuracy、per-class P/R/F1、**未加权** macro-F1（round 4 位）|
| 对话通过线 | `overall >= 0.75`（硬编码）|
| Judge | 4 维 0~1，`overall = 四维均值`，temp 0.0 / ≤256 tokens |
| Judge 兜底 | 缺字段回退 **0.5**；异常 → 全 0.5 + `judgeFailed=true` + error 入 metadata |
| baseline | `data/eval/baseline.json`，**每次运行先比后覆盖**；退化判定 `(cur−prev)/prev < −5%` |
| 重要缺陷 | 评测链路**绕过** AnswerVerifier / 记忆 / 知识库 / 画像 → **评测与线上不同构** |

## 5. 高频追问 30 问

### A. 意图识别

**Q1 三路权重 0.7/0.2/0.1 怎么定的？**
初值按"LLM 语义最强、字面次之、规则最稳但最笨"给，再用内置标注集调。深挖：权重是硬编码常量（`IntentRecognizer` 里的 `addScore` 调用），没做成配置项——这是我认知里的待改点。

**Q2 三路给出不同意图怎么办？**
按权重加权求和取最高。另有一次"通用意图→细粒度"的修正（比如 TECHNICAL → TECHNICAL_LOGIN）。深挖：这是启发式不是概率融合；正路是每路输出完整分布再做加权 Borda 或逻辑回归。

**Q3 LLM 挂了会怎样？**
解析失败 → `confidence=0.0`，不给分；规则路和语义路继续投票。`baseline.json` 里那次跑批全是 "LLM 失败"，意图准确率仍有 **81.8%**（9/11）、Macro-F1 0.692——这就是降级路径的真实效果，**别把它说成"LLM 加持下的准确率"**。

**Q4 19 个意图会不会太细？**
细类来自 `IntentCategory` 枚举 + prompt 里的类别清单，稳定靠"枚举约束 + 规则兜底"，不是靠模型自由发挥。深挖：默认评测用例的 `expectedIntent` 是**粗粒度**（technical / escalation），而系统会修正到细粒度（technical_crash / human_handoff），所以那条用例本身就会判错——这是"口径冲突"，正确做法是用 `intentGroup` 归一化比对。

**Q5 意图识别错了下游会怎样？**
两个后果：路由到错 Agent，或该不该检索判错。可观测性上能区分——返回里有 `intent`、`intent_group`、`routing_reason`（含各 Agent 得分）、`knowledge_used`。深挖：没有人工纠错回流机制。

### B. 编排

**Q6 为什么 supporting 要同时满足 ≥0.45 和 ≥ primary×0.55？**
0.45 是"够格参与"的绝对门槛，×0.55 是"别把明显不相关的拉进来"的相对门槛，两个都满足才并行，避免每次请求都变成多 Agent、把延迟放大。

**Q7 多 Agent 的结果怎么合并？**
**结构化字符串拼接**，每条带 `[technical - 主处理]` 前缀。这样可预测、省一次 LLM 调用；代价是读起来像清单。深挖：要更自然就得加一次"Response Composer"调用，成本 +1 次 LLM、延迟 +几百毫秒——Python 版就是这么做的，Java 版选择了省。

**Q8 并行用什么线程池？风险？**
`CompletableFuture.supplyAsync` 不传 executor → `ForkJoinPool.commonPool`，和全局流共享、无隔离；正确做法是给编排单独一个受控线程池（有界队列 + 拒绝策略）。

**Q9 某个 Agent 一直失败怎么办？**
两层：单请求内，非 general 失败会退回 GeneralAgent 重答一次；跨请求，`AgentStats` 记录成功率与延迟，Monitor 算 penalty 写进 `routingScore`。但**每类型只有一个实例**，所以跨请求这层现在主要是可观测，不是真切换（见第 4 节真相 3）。

**Q10 路由原因里那些数字是什么？**
`routing_reason` 是 `intent=…, primary=…, supporting=…, scores=[billing=1.50, technical=0.93]` 这样的字符串，直接暴露各 Agent 的打分结果——出问题能判断是"意图错"还是"打分错"。这是这套系统最值钱的可观测性设计。

### C. RAG

**Q11 切片怎么切？为什么 500/80？**
LangChain4j `DocumentSplitters.recursive(500, 80)`：先按段落、再按句子递归下切到 500 字符以内，80 是重叠（16%），防止跨段条款被切断。深挖：rerank 时每条只截 180 字，所以 chunk 不能太大，否则尾部内容根本进不了 rerank 的视野——这是"500 而不是 1024"的真实理由。

**Q12 两路分数怎么融合？为什么不是 RRF？**
各自除最大值归一后线性加权 0.45/0.55。RRF 的好处是不用校准尺度，代价是不可解释；两路共线时 RRF 也救不了，所以先选了线性。

**Q13 这个"向量"到底是什么？**
256 维 signed feature hashing：把 token 集合（HashSet，丢词频）映射到 256 个桶，符号由 `hash & 1` 决定。不是模型、没有训练、没有语义。

**Q14 那"混合检索"还有什么意义？**
老实说：语义增量很小，因为它和 BM25 共用 tokenizer。真实增量有三点——① 向量侧丢词频、不施加 BM25 的长度惩罚，短 chunk 不被压制；② 256 桶折叠带来粗糙的近形合并（也带碰撞噪声）；③ 双路归一后再加权，等于对极端高分做二次压制。要做真语义召回就换 EmbeddingModel，并把融合改 RRF。

**Q15 ChromaDB 用在哪？**
容器在 compose 里、配置也有 `pudding_knowledge` collection，但 Java 侧两个 profile 都排除了 `ChromaVectorStoreAutoConfiguration`，`vectorStore` 恒 null，写入是空操作。**Python 版才是真接 Chroma**。要接回来就是去掉 exclude + 写后走 VectorStore。

**Q16 召回为什么不直接给 20 条？**
`recallK = max(topK,5)`，每子查询 5 条、4 路去重后最多 20 条候选，再 rerank 到 3 条。给太多会让 rerank prompt 变长（每条 180 字，20 条≈3.6k 字符）且尾延迟上升。

**Q17 rerank 失败会怎样？**
回退到**融合分排序**（不是原始召回顺序——原始顺序是"子查询顺序"，没有相关性含义）。深挖：回退时 `reranked` 仍是 true，标志不可信。

**Q18 中文分词做了吗？**
没有。`\p{Punct}` 只剥 ASCII 标点，中文全角标点会留在 token 和 n-gram 里；没有停用词表、没有分词器。规模一大就该换 Lucene/ES 或 jieba。

### D. 稳定性与工具治理

**Q19 熔断器怎么工作？**
CLOSED 放行；失败累计到 5 次转 OPEN，60s 内直接拒绝并返回降级文本；60s 后第一次 `allow()` 转 HALF_OPEN 放行探测；成功清零回 CLOSED，失败立刻回 OPEN（`failCount` 不清零）。深挖：HALF_OPEN 期间**全量放行**、没有"只放一个探测"的限制，并发下有惊群；而且真正能打开它的只有超时（见第 4 节真相 4）。

**Q20 超时怎么控？**
只有 `future.get(30s)` 一个中断点，且**不 cancel**，LLM 请求会继续跑；LLM 层没有超时配置，最坏 4×30=120s。正确做法：专用线程池 + `orTimeout` + HTTP 层超时 + 全请求总预算。

**Q21 工具失败会不会让整条回复失败？**
不会。熔断/超时/异常三条路径都返回 `success=true` 的降级结果（`metadata.fallback=true`），降级文本会进上下文并提示转人工。代价是故障可能被静默吞掉，所以 `/monitor` 里有工具成功率和熔断状态。

**Q22 缓存怎么设计的？命中率多少？**
key=`query:topK`，TTL 300s，懒过期，无上限无 LRU，粒度是**子查询**所以 rerank 每次重算。命中率拿不出来——代码里没有 cache hit 计数器，而且外层 `cached` 标志是硬编码 false。另外它是普通 `HashMap`，并发不安全。

### E. 记忆

**Q23 记忆怎么分层的？**
Redis 两个 key：`wm:{uid}:{cid}` 存工作记忆（List，最多 20 条，TTL 86400s），`summary:{uid}:{cid}` 存摘要。情节记忆在进程内 `CopyOnWriteArrayList` + 自研 256 维 hash 向量，扫 top5 注入 3 条；用户画像是 `ConcurrentHashMap` + JSON 文件。**除了工作记忆和摘要，其余都不在 Redis**——别答错。

**Q24 压缩怎么做的？**
消息数到 15 触发，同步调 LLM 总结成 2-3 句（temp 0，失败兜底"对话包含 N 条历史消息"），然后**只保留最近 5 条**并删 key 回填，摘要追加进 summary key。深挖：因为只留 5 条，实际约每 10 条消息就再触发一次；压缩是同步的，会加在一次 /chat 的尾延迟里。

**Q25 为什么不用一个大 list 全塞上下文？**
token 成本和注意力衰减：越远的对话越不相关，摘要比原文抗噪。代价是会丢细节，所以只压早期对话、最近 15 条保原文，并要求摘要保留关键实体。

### F. 监控与评测

**Q26 LLM-as-Judge 靠谱吗？**
三个已知问题：同模型自评有偏好（judge 与被评同 provider）、无参考答案时偏印象分、分数抖动。现有缓解只有四道闸：`temp=0`、四维拆解、clamp 到 [0,1]、缺字段/异常回退 0.5 并标 `judgeFailed`。**没有** rubric 锚点、参考回答、多次采样、换位比较。更严谨就上双模型交叉 + 人工抽检。

### G. 三个最容易被追问的细节

**Q27 "三路投票里权重 0.7 是不是等于模型说了算？"**
基本是。因为**没有归一化**：模式路满分只有 0.10、语义路满分 0.20，所以过 0.5 阈值几乎只能靠 LLM（单靠 LLM 需 `conf ≥ 0.714`）。
所以真实机制是"**LLM 决定够不够格 + 关键词负责把粗粒度改细**"：refine 规则里 `best<0.8` 恒成立（`0.7×conf≤0.7`），
句子里出现细粒度关键词（401、发票、物流）时，关键词表几乎总会覆盖 LLM 的粗分类。
深挖：这说明"投票"更接近"分层决策"；要做真投票得先给三路各自归一化，再融合。

**Q28 "低置信度会怎么处理？会多轮澄清吗？"**
`intent==OTHER` 且消息长度 >2 且 `confidence<0.5` 时，返回固定话术"我还不能确定您要处理的是哪类问题…"，
`agentType=GENERAL`、`escalated=false`、`routingReason="低置信度 OTHER 意图，先澄清用户需求"`。
**只做一轮，没有多轮槽位填充**；如果 `OTHER` 但 `conf≥0.5`，不澄清、直接进 GeneralAgent。

**Q29 "AnswerVerifier 会把不合格的回答拦下来吗？"**
不会。它只**标注**：`pass=false` 只体现为响应里 `verified=false`，不重写、不重新生成、不拦截；
唯一影响业务的出口是 `need_escalation` 把 `escalated` 抬成 true。而且它是 fail-open 的——
LLM 出问题时兜底 `pass=true`，`grounded` 取"上下文是否非空"，等于校验静默失效。
（顺带：这里 `substring` 没校验 `start>=0`，模型不吐花括号时会抛 `StringIndexOutOfBounds` 落到兜底。）

**Q30 "ESCALATION 有专属 Agent 吗？"**
枚举有、路由表也指向它，但 `AgentConfig` 里**没注册** ESCALATION 实例，所以走"目标类型不在 pool → 回落 GENERAL"这条降级：
返回里会看到 `primaryAgent=escalation` 而 `agentType=general`。这不是 bug 而是"转人工作为流程终点"的设计，
但如果被问"转人工是谁答的"，要答准：**是 GeneralAgent 用兜底话术回应的**。

## 6. 最刁钻的 10 个问题

1. **"你的多 Agent 是真协作还是三个 prompt 拼一起？"**
   并行是真并行（CompletableFuture），但合并是字符串拼接，没有二次统一润色。所以准确说法是"并行分工 + 结构化汇总"。

2. **"你说降权，效果怎么量化？"**
   给不出线上数据——没跑真实流量。能给的：`/monitor` 里每个实例都有 `success_rate / avg_ms / monitor_penalty / routing_score`，指标端点有 Gauge；缺的是"开关 penalty 前后"的对比实验，而且每类单实例意味着它现在对路由没有实际影响。

3. **"知识库里没有的问题怎么办？"**
   可能召回低分片段，融合后仍会取前 3；靠 `AnswerVerifier` 判断是否基于上下文，拿不准就 escalated。缺一个"最高分 < 阈值就不注入"的门槛。

4. **"BM25 自己写的？为什么不用 Lucene？"**
   手写约 30 行，零依赖、可解释、便于演示；代价是没有倒排索引——`df` 在内层循环里对每个 term 重新 tokenize 全库，复杂度约 O(N²·T)，几百 chunk 就会吃 CPU。规模上去就该换 Lucene/ES。

5. **"换个业务能用吗？"**
   能，但改三处：`IntentCategory` 枚举 + 关键词表、`skills/*/SKILL.md`、`domainScores` 的领域规则。所以它是"配置化的客服框架"，还不是"通用 Agent 平台"。

6. **"重做一遍先改哪？"**
   ① 把 penalty 乘进 domainScores，让降权真正影响跨 Agent 选择；② 线程池/超时/缓存收进配置并加隔离；③ 评测纳进 AnswerVerifier，解决"线上与评测不同构"。

7. **"评测准确率多少？"**
   `baseline.json`（Python 版那次）里 intent_accuracy 0.818、macro_f1 0.692，但那是 **LLM 全失败**下的降级结果，且期望标签与细粒度预测口径不一致。**Java 版 `data/eval/` 目录当前是空的，没有基线**——这个必须说实话，别报一个自己没跑过的数。

8. **"你的 latency_ms 是端到端吗？"**
   不是，只统计编排段（意图、检索、校验、记忆写回都不含）。要端到端就在 Controller 层再加一个计时。

9. **"告警怎么闭环？"**
   没闭环：`alertKeys` 永久去重、`resolved` 恒 false、没有恢复通知；webhook 默认没配、`RestClient` 无超时无重试、异常全吞。也就是"能告一次警，不能跟踪恢复"。

10. **"这套东西只在你自己机器上能跑吗？"**
    不是：`docker compose` 一键起 Redis + Chroma + Prometheus + Nginx，配置全走环境变量，有 `/health` 探针；检索不依赖外部向量库。注意对外端口是 6380 / 8002 / 9091，不是默认端口。

### 被问"你具体做了什么"怎么答

最稳的结构是**分层 + 不越界**：

> 这个项目的骨架是基于一份已有的多 Agent 客服实现，我的工作主要在四块：
> ① **工程化**：把命名、包结构、配置项（`pudding.*`）、Skills 人设、前端品牌统一成布丁智服这一套，并从 Python 版对照重构到 Java；
> ② **可运行性**：补齐 Docker Compose（Redis / Chroma / Prometheus / Nginx）、健康检查、环境变量与 `.env.example`，让 `docker compose up` 能直接跑起来；

> ④ **文档**：README、接口说明、面试文档。
> 算法侧的设计（三路投票、领域打分、混合召回）我逐行读过、能讲清取舍，但我不声称是我原创的。

这样答的好处：**边界清楚，可信度高**，而且对方后续提问会集中在你能答的部分。

## 8. 主动亮短板的三句话

面试里主动说这三个，效果比藏着强得多——每个都配"我会怎么改"：

1. **「降权机制只做到一半」**：penalty 能算、能回写、能观测，但没乘进领域打分，加上每类单实例，所以跨 Agent 迁移还没闭环。改法：`domainScores` 出来后 `score *= (1 − penalty)`。
2. **「并发与超时不够严谨」**：编排和检索都走 commonPool；超时只在 `future.get(30s)`、不 cancel；缓存是 HashMap。改法：专用线程池 + `orTimeout` + HTTP 超时 + `ConcurrentHashMap` + 容量上限。
3. **「测试是短板」**：Java 侧无单测，靠内置评测集兜底。改法：`IntentRecognizer` 参数化用例、`CircuitBreaker` 状态机单测、编排用 Mock LLM 做集成测试；再把 `/eval/run` 接进 CI。

```bash
cd pudding-java && cp .env.example .env   # 填 Key
docker compose up -d --build
curl http://localhost:8080/health

# 复合问题：看路由原因与知识库命中
```

## 附录 B：术语与易混概念

| 概念 | 本项目里的意思 | 别混成 |
|---|---|---|
| 哈希向量 | 256 维 signed feature hashing | embedding / 语义向量 |
| 混合召回 | BM25 + 哈希向量线性融合 | dense + sparse 双路语义检索 |
| 三路投票 | 1 次 LLM + 2 路本地运算，**无归一化** | 三个模型投票 / 加权平均概率 |
| refine | 关键词表把粗粒度意图改细 | LLM 自己判出细粒度 |
| 熔断 | 连续失败 5 次 → 60s 拒绝 | 限流（本项目**没有**限流）|
| 惩罚分 penalty | 监控算出的降权系数，进 routingScore | 直接把流量切给别的 Agent |
| 路由（routing） | 选 Agent 类型 + 选实例 | 负载均衡 |
| Skills | `SKILL.md` 里的业务规范，按关键词注入 prompt | 插件 / 工具（工具是 knowledge_search）|
| 校验（verify） | 只标注 `verified` / `escalated` | 拦截、重写、重生成 |
| 评测 | `/eval/run` 跑意图指标 + Judge 打分 | 单元测试 / 压测 |
| latency_ms | 只含编排段 | 端到端耗时 |

## 附录 C：7 小时掌握路径（含动手任务）

> 光读代码记不住。按这个顺序走一遍，最后你会有一段"我自己改过、能讲清为什么这么改"的经历——这是面试里最硬的底气。

| 时长 | 做什么 | 产出（能写进简历的一句话） |

| 1h | **读 RAG 两个类**：`KnowledgeBaseService`（BM25/hash 向量/融合）与 `KnowledgeToolManager`（改写/并发/重排/缓存/熔断） | 能讲清"为什么这个向量不是 embedding" |
