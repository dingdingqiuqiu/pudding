监控与评测：Prometheus 采集 Agent 成功率与延迟并回写路由做动态降权，评测覆盖意图 Accuracy 和 LLM-as-Judge 四维打分，支持 baseline 回归检测；

## 面试怎么讲（三个层次，按时间长短选）

**30 秒版**

> 布丁智服是我做的一个多 Agent 客服系统。用户问题进来先做意图识别，再路由给通用、技术、账单三个 Agent；
> 复合问题会拆成主 Agent + 辅助 Agent 并行处理再合并。知识库检索是按意图触发的，避免每句话都去查 RAG。
> 整个链路有 Prometheus 指标和 LLM-as-Judge 评测，能看出哪一步退化了。

**2 分钟版（讲清"为什么这么做"）**

1. **为什么要意图识别，而不是直接丢给大模型？**
   客服问题的处理动作是分叉的：退款要核对订单、登录异常要排障、投诉要转人工。
   如果只靠一个 prompt，模型会"什么都答一点"，答不到点上，还会编造订单状态。
   所以先用三路投票把意图定死，再决定查不查知识库、走哪个 Agent、要不要人工。
2. **为什么要多 Agent，而不是多个 prompt？**
   不同业务的话术规范不一样，且要能各自独立调优、独立监控。
   拆成 Agent 之后，每个 Agent 有自己的 system prompt + 自己的 Skills，路由层只负责决策；
   某个 Agent 成功率掉了，Monitor 会给它扣分，后续流量自动少分给它。
3. **RAG 为什么要按意图触发？**
   问候、感谢、转人工这类请求检索是纯浪费，还会把无关知识片段塞进上下文造成答非所问。
   所以先看意图，只对业务类意图检索；检索内部再做查询改写、并行召回、重排，最后交给模型。
4. **怎么证明它变好了？**
   意图识别用标注集算 Accuracy / Macro-F1；端到端用 LLM-as-Judge 从相关性、准确性、完整性、有用性四个维度打分，
   存 baseline，下一轮退化超过阈值就标记 regression。

**可能被追问的点**

| 追问 | 回答要点 |
|---|---|
| 三路投票权重怎么定？ | 先给初值（LLM 0.6 / 相似度 0.25 / 规则 0.15），再用标注集做网格搜索；低置信度时走澄清而不是硬答。 |
| 路由打错了怎么办？ | 每条回复都带 `primary_agent`、`supporting_agents`、`routing_reason`、`routing_confidence`，线上能直接看是意图错了还是打分错了。 |
| 熔断/降级怎么设计的？ | 工具层统计成功率和延迟，连续失败进熔断，期间直接走 fallback；回复侧 `AnswerVerifier` 兜底，必要时转人工。 |
| 记忆为什么要分 Redis 和向量库？ | 工作记忆要快、要按会话读写（Redis）；长期摘要和用户画像要语义检索（向量库）。向量库操作同步会阻塞主链路，所以放线程池。 |
| 为什么有 Python 版还有 Java 版？ | Python 版验证能力和算法，Java 版按企业级服务的要求重写：Spring 生态、Actuator/Prometheus、Swagger、Docker Compose 一键部署。 |
| 数据规模多大？有没有压测？ | 按真实情况答，不要编数字；可以说"目前是内置评测集 + 本地压测，还没做大规模线上验证"。 |
